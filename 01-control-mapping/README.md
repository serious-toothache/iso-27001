# 01 · Control Mapping: ISO/IEC 27001:2022 Annex A → Real Configuration

**File:** [`annex-a-control-mapping.csv`](annex-a-control-mapping.csv) (Searchable table)
## What I built

A mapping of 18 ISO/IEC 27001:2022 Annex A controls to the concrete technical implementations that satisfy them in an AWS + GitHub environment, with a SOC 2 crosswalk. Each row answers the questions an auditor would ask:

| Column | Question it answers |
|---|---|
| `requirement_in_plain_words` | What is the control actually asking for? |
| `aws_implementation` / `github_implementation` | What configuration makes it true? |
| `evidence_artifact` | What proves it, without a screenshot? |
| `automated_check` | Is there code in this repo that tests it? (links to [02-evidence-collection](../02-evidence-collection)) |
| `test_procedure` | How would an auditor test it: inquiry, inspection, observation or re-performance? |
| `soc2_tsc` | Which SOC 2 Trust Services Criteria the same evidence satisfies (*test once, satisfy many*) |
| `scope` | Is the service **global** (test once) or **regional** (test in every in-scope region)? |
| `sampling_strategy` | Which slice gives enough confidence: entire population, module n = 1, entity, event-type, anomaly or temporal ([rationale](../08-evidence-evaluation/sampling-rationale.md)) |
| `cge_aud_domain` | Which CGE-AUD domain the test technique comes from ([ALIGNMENT.md](../ALIGNMENT.md)) |
| `workpaper` | Where the control is actually tested in this repo |

## Why I built it this way

**A control is only as real as its configuration.** "We enforce MFA" is a policy statement. `mfa_active = true` for every row in the IAM credential report is a fact. The gap between those two is where most audit findings live, so the mapping goes all the way down to the setting.

**Two systems, one control.** Modern companies run on cloud *and* source control. A.8.5 (secure authentication) is not satisfied if AWS enforces MFA but GitHub does not. Splitting the implementation column by platform forces me to cover both.

**Evidence and tests are part of the mapping, not an afterthought.** If I can't name the evidence and the test, the control isn't auditable yet. Eleven rows link to an automated check. Those are the controls whose evidence can be generated by code instead of collected by hand.

## Decisions and trade-offs

- **ISO/IEC 27001:2022** is the certification I hold, so it's the framework I chose to put into practice.
- **SOC 2 as a crosswalk, not a second audit.** One collection, one test, two citations. The collector writes both `iso27001_2022_annex_a` and `soc2_tsc` into every evidence file. The crosswalk is my own judgement against the TSC points of focus, not an official mapping.
- **18 controls, not 93.** I chose the controls where technical configuration carries most of the weight, plus a few organizational controls (A.5.19, A.5.24) to show the mapping isn't only about cloud settings. The Statement of Applicability in a real ISMS would justify inclusion or exclusion of all 93.
- **Plain-language requirements.** The control descriptions are my own paraphrases. ISO text is copyrighted, and rewriting each requirement in plain words is also the best test that I understand it.
